## 1. Зачем

Loom — **настраиваемая IDE для ACP-агентов**: десктопное приложение, в котором и интерфейс, и поведение целиком собираются из плагинов. Сам Loom — это фундамент: ядро, механизмы расширения и минимальный набор плагинов, с которым можно поговорить с агентом. Всё предметное — визуализации результатов агента, оркестрация нескольких агентов, интеграции с внешними системами, особые раскладки — делается плагинами и в этот документ не входит. **[решено]**

Разработчик любой специализации собирает себе свою «сборку»: набор плагинов и конфиг.

Ориентир по философии — [Pi](https://github.com/badlogic/pi-mono): минимальное ядро, всё остальное ставится пакетами. Разница с Pi: у нас настоящий графический интерфейс, и плагины могут менять его целиком.

## 2. Цели, не-цели, анти-цели

**Цели**
- Минимальное ядро, в котором нет ничего предметного. Чат, раскладка, настройки, ACP-клиент — плагины. **[решено]**
- Любая часть интерфейса заменяема плагином: корень, раскладка, шапка, сайдбары, правые островки, лента чата, отображение сообщений, поле ввода, меню приложения, настройки. **[решено]**
- Плагин может зависеть от другого плагина и встраиваться в его входы (например, добавить секцию в настройки, которые сами являются плагином). **[решено]**
- Плагин может дать агенту свои инструменты и вмешиваться в ход агента (разрешать, запрещать, менять вызовы, дополнять промпт) настолько глубоко, насколько позволяет конкретный агент. **[решено]**
- Системные возможности (файлы, терминал, git, окна, трей, хоткеи, уведомления) тоже расширяются плагинами без пересборки приложения. **[решено]**
- Плагины подтягиваются на лету: установил или изменил плагин — изменения видны без перезапуска приложения. **[решено]**
- По умолчанию ставится «сырая» минимальная сборка; красивый интерфейс собирается поверх неё. **[решено]**
- Спокойные, плавные анимации без скачков интерфейса. **[решено]**

**Не-цели (первый этап)**
- Маркетплейс плагинов и публикация в общий каталог.
- Веб-версия и командная работа. Только десктоп. **[решено]**
- Любые предметные возможности: визуализации работы агента, оркестрация и воркфлоу из нескольких агентов, интеграции (Jira, Figma и т. п.). Это будущие плагины, фундамент лишь даёт для них механизмы. **[решено]**
- Свои MCP-серверы для внешних систем — это забота самих агентов. **[решено]**
- Песочница для установленных плагинов (см. модель доверия).

**Анти-цели — даже если работает, это провал**
- Ядро, которое знает о чате, агентах или конкретной раскладке.
- Закрытые списки в коде (`switch` по фиксированному набору панелей, union-типы с перечислением всех вкладок), из-за которых новый плагин требует правки ядра. Это главная болезнь всех трёх изученных проектов.
- Плагин, который молча теряет силу: если агент не умеет того, что плагин просит, плагин должен об этом узнать.
- Интерфейс, который скачет при обновлении данных или при появлении нового агента.

**Аудитория [решено]:** приложение распространяется среди других разработчиков, не только для личного использования. Отсюда:
- подписанные и нотаризованные сборки для macOS и автообновление (electron-updater, релизы на GitHub) входят в план с самого начала **[механизм — моё]**;
- API плагинов — публичный контракт: semver, отчёты api-extractor, документация для авторов, шаблон плагина (`create-loom-plugin`) **[моё]**;
- формат сборки (пакет с зависимостями и `loom.config.json`) — тоже публичный контракт с версией схемы **[моё]**;
- платформы: сначала macOS; Windows и Linux собираются в CI с первого дня, но поддерживаются после первого среза **[моё]**;
- сбор аналитики по умолчанию выключен, отчёты о падениях — только с согласия **[моё]**.

## 3. Ограничения

- Платформа: десктоп, Electron. Основной пользователь работает на macOS. **[решено: десктоп; Electron — моё]**
- Ядро агентов: ACP. **[решено]**
- Плагины доверенные: работают внутри приложения с полным доступом. **[решено]**
- Код можно заимствовать из harnss (MIT), pi-gui (MIT), AionUi (Apache-2.0), claude-agent-acp (Apache-2.0) с соблюдением лицензий.

## 4. Архитектура

### 4.1 Процессы и слои

В main-процессе (Node) и в окне (React) работают одинаковые слои: **ядро → `@loom/sdk` → плагины**. У каждого плагина может быть вход для main и вход для окна. Ядра двух процессов связаны типизированным RPC: сервис, предоставленный в main, автоматически доступен в окне по тому же токену. Main-процесс общается с ACP-агентами. **[моё]**

### 4.2 Сущности ядра

Подробно с примерами — на странице [Ядро Loom](https://claude.ai/artifact/YTtvHnao66MkxxxTFjziL5). Классический DI-контейнер с декораторами не используется. **[решено]**

| Сущность | Вопрос, на который отвечает | Суть |
|---|---|---|
| Плагин | Что поставляется одним пакетом? | npm/git/локальный пакет; `package.json` с полем `loom`: `id`, `dependsOn` (обязательные и необязательные `?`), входы `main` и `renderer`, `settingsSchema`, блок `startup` |
| Сервис | Кто умеет это делать? | Объект по типизированному токену (`createServiceRef`). Один поставщик на токен. `provide`, `use`, `override`, `decorate`. Потребитель получает живую ссылку, которая при вызове берёт текущего поставщика |
| Расширение и вход | Где это стоит в интерфейсе? | Модель из Backstage: у расширения есть `attachTo { id, input }`, свои входы и `factory`. Корень `app` — тоже расширение. Вывод проверяется по схеме входа |
| Хук | Кто может вмешаться и поменять результат? | Конвейер middleware `(ctx, next)`; порядок по `priority`, `before`, `after`; фильтр `match`. Хуки объявляют плагины, которым принадлежит действие, а не ядро |
| Событие | Кому сообщить, что что-то случилось? | Рассылка после факта, без влияния на результат |

Способы изменить чужое: `override` (замена по id), `disable`, `decorate` (обёртка сервиса), `next()` в хуке (обёртка поведения), перецепка `attachTo` в конфиге пользователя.

Конфликты не разрешаются молча: два поставщика одного сервиса или две замены одного расширения — ошибка при запуске с предложением выбрать в конфиге.

### 4.3 Ядро

Обязанности: загрузчик (поиск, проверка манифестов по схеме, доверие, топологическая сортировка), реестр сервисов, реестр хуков, шина событий, сборщик дерева расширений, RPC между процессами. Оценка объёма — 600–1000 строк. **[моё]**

Единственный собственный сервис ядра — `PluginsRef`: `install`, `uninstall`, `enable`, `disable`, `reload`, `list`; `reconcile` плагинам недоступен (вызов из `setup` заблокировал бы собственную очередь пересборок — взаимная блокировка), его вызывает только хост; хук `plugins.beforeInstall`; события `plugins.changed`, `plugins.failed`.

### 4.4 Пересборка на лету **[решено: нужна; механизм — моё]**

Запуск — частный случай `reconcile()`: «было пусто, стало N». Алгоритм:
1. Проверить новый набор и построить граф до любых изменений.
2. Посчитать разницу: добавлены, удалены, изменены.
3. Затронутые = изменённые и удалённые плюс все, кто от них зависит транзитивно. Новые плагины никого не перезапускают.
4. Сохранить снимок старых версий, выгрузить затронутых в обратном порядке (снимается всё, что они зарегистрировали).
5. Поднять затронутых и добавленных в прямом порядке, передать каждому сохранённый `ctx.state`.
6. При ошибке откатить к снимку и выпустить `plugins.failed`.
7. Пересобрать дерево расширений, разослать изменения ядру окна.

Сохраняется: состояние React-компонентов (ключ — id расширения), `ctx.state`, данные в `storage`, сессии агентов (при перезапуске `acp` — переподключение через `session/load`). Требует перезапуска приложения: изменение блока `startup` и нативных модулей; ядро сообщает это явно.

В режиме разработки ядро следит за папками локальных плагинов, пересобирает изменённый (esbuild) и вызывает `reload(id)`.

### 4.5 Модель доверия **[решено]**

- Установленные плагины работают внутри приложения с общим React и полным доступом (как в Obsidian и Pi). Защита — доверие к проекту (проектные плагины грузятся только после явного согласия) и проверка кода.
- Недоверенный контент (например, HTML, сгенерированный агентом) плагины показывают только в изолированном iframe без сети. Ядро даёт для этого готовый компонент; механизм можно взять из pi-gui (`sandbox="allow-scripts"`, отдельный протокол, CSP, MessagePort). **[механизм — моё]**

## 5. Агенты

### 5.1 ACP как ядро **[решено]**

Плагин `acp` реализует ACP-клиент. Базовый уровень доступен любому агенту:
- `session/request_permission` → хук `acp.toolCall` с исходами `allow` / `deny`;
- клиентские `fs/*` и `terminal/*` → через плагины `fs` и `terminal` и их хуки, если они установлены;
- `session/prompt` → хук `acp.prompt` для добавления контекста;
- параметры `session/new` (`cwd`, `env`, `mcpServers`, нестабильное поле `systemPrompt`) → хук `acp.sessionConfig`;
- поток `session/update` → события.

Ограничение базового ACP: агент сам решает, о чём спрашивать; входные данные вызова менять нельзя.

### 5.2 Глубина через плагин-адаптер **[решено]**

Плагин `claude-code` регистрирует агента с собственным адаптером — форком [claude-agent-acp](https://github.com/agentclientprotocol/claude-agent-acp). Адаптер в хуках Claude Agent SDK (`canUseTool`, `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `PreCompact`) отправляет клиенту ACP-расширения вида `_loom/hook/*`. Агент объявляет возможности (`modifyToolInput`, `gateReads`, `postToolUse`, `compactHooks`), и плагин `acp` направляет хуки через самый глубокий доступный канал. В `ctx` хука есть `canModify`, чтобы плагин знал, что ему доступно. **[механизм — моё]**

Правки адаптера держатся тонким слоем поверх upstream, чтобы подтягивать его обновления. **[моё]**

### 5.3 Инструменты для агента **[моё]**

`agent-tools`: реестр инструментов плагинов (`name`, `description`, `schema`, `run`), отдаётся в каждую сессию как MCP-сервер. Через него любой плагин даёт агенту возможность управлять своим интерфейсом или данными.

## 6. Интерфейс

### 6.1 Контракт раскладки **[решено]**

Входы раскладки названы по роли: `titlebar`, `navigation[]`, `primary`, `auxiliary[]`, `status[]`. Любая раскладка принимает все роли и сама решает, где их показать. Раскладка может открывать дополнительные входы. Расширения, которым не нашлось места, показываются в списке «не прикреплены» с подсказкой, как перецепить.

Корень `app`: входы `providers[]`, `layout`, `screens[]`, `overlays[]`; сервис `NavigationRef`; текущий экран подставляется в роль `primary`.

### 6.2 Сборки **[решено]**

| Сборка | Состав |
|---|---|
| Только ядро | пустое окно «плагины не установлены» |
| Минимальная (по умолчанию) | ядро + `storage`, `acp`, `claude-code`, `app`, `layout-bare`, `chat`, `composer`. Лента и поле ввода, ответы простым текстом |
| Полная из комплекта | минимальная + остальные плагины из раздела 6.3 |
| Своя | любые плагины + `loom.config.json`. Сборка — пакет без кода: зависимости и конфиг |

### 6.3 Плагины из комплекта

Полный список с сервисами, входами, хуками и событиями — на странице [API плагинов Loom](https://claude.ai/artifact/8M6X2RSWqkSgd1x25xiKPA). Кратко: **[моё]**

- система (main): `storage`, `fs`, `terminal`, `git`, `windows`, `tray`, `shortcuts`, `notifications`, `protocol`, `commands`;
- агенты: `acp`, `agent-tools`, `claude-code`;
- каркас: `app`, `theme`, `layout-bare`, `layout`, `titlebar`, `sidebar`, `sessions`, `islands`, `statusbar`, `menu`, `dialogs`, `palette`;
- чат: `chat`, `markdown`, `composer`, `settings`.

Меню приложения, палитра ⌘K и хоткеи не держат свои действия, а ссылаются на команды из `commands`. Плагин может объявить `settingsSchema`, и секция настроек построится автоматически.

### 6.4 Островки

Правые панели в стиле harnss: стопки, колонки, разделение, перетаскивание, сохранение раскладки. Каждая вкладка — расширение на вход `islands/panels` с метаданными `{ id, title, icon, component, minWidth, defaultDock }`. Раскладка островков не опирается на фиксированный набор вкладок. **[решено: как в harnss, через пакеты]**

### 6.5 Дизайн

Каркас знаком по агентским IDE (Claude Code, Codex, Cursor): сайдбар, чат, панели справа. Всё оформление — CSS-токены темы; цвет — только для статуса. Анимации плавные, без смены раскладки при обновлении данных; новая сессия или панель не перехватывает фокус, а ставит отметку. Плагины строятся на общем пакете дизайн-системы `@loom/ui`. **[решено: простота и сходство; токены и `@loom/ui` — моё]**

## 10. Структура репозитория **[строителю, ориентир]**

```
packages/
  kernel/        ядро (main и окно)
  sdk/           публичный API для плагинов
  ui/            дизайн-система
plugins/
  storage/ acp/ claude-code/ app/ layout-bare/ chat/ composer/   минимальная сборка
  ...            остальные плагины из комплекта
adapters/
  claude-agent-acp/   форк адаптера
apps/
  desktop/       Electron-оболочка: загрузка ядра, preload, упаковка
builds/
  minimal/       сборка по умолчанию
```

`plugins/*` — отдельные пакеты рабочего пространства, публикуются независимо друг от друга. Правило: `packages/*` никогда не импортирует `plugins/*` (ядро, SDK и UI не знают о конкретных плагинах). Проверка добавляется в линтер вместе с первым плагином.

## 10a. Этап 1 — только ядро **[решено]**

Первый этап — пакеты `@loom/kernel` и `@loom/sdk` без Electron и без единого плагина из комплекта: загрузчик, сервисы, хуки, события, дерево расширений, `reconcile()`, RPC между процессами. Требования: полное покрытие тестами, работа без оговорок (никаких «известных ограничений» в поведении из раздела 4), оптимизация с замерами. Проект живёт в GitHub-репозитории с CI.

Ядро на этом этапе не зависит от платформы: работает в Node и в браузере, транспорт RPC абстрактный. React-привязка дерева, Electron-оболочка и плагины — следующие этапы. **[моё]**

## 10b. Этап 2 — минимальная сборка **[решено: объём; устройство — моё]**

Цель: окно Electron, в котором можно поговорить с Claude Code в выбранной папке — сообщение, ответ, вызовы инструментов, запросы разрешений. Ничего больше.

| Пакет | Где работает | Что делает |
|---|---|---|
| `apps/desktop` | Electron | ядро в main и ядро в окне, RPC по `MessagePort`; выбор папки проекта системным диалогом; плагины сборки подключаются статически через виртуальные модули Vite |
| `packages/react` (`@loom/react`) | окно | `KernelProvider`, `useService`, `useHookRunner`, `<Render node>` |
| `plugins/storage` | main | ключ-значение в JSON-файлах (атомарная запись) |
| `plugins/acp` | main + окно | main: ACP-клиент, реестр агентов, сессии, разрешения; окно: удалённый прокси того же сервиса под тем же id |
| `plugins/claude-code` | main | регистрирует агента `claude-agent-acp` (без форка), запуск через Node из Electron |
| `plugins/app`, `plugins/layout-bare` | окно | корень и раскладка «только primary» |
| `plugins/chat`, `plugins/composer` | окно | лента сессии и поле ввода |
| `builds/minimal` | — | сборка: зависимости + `loom.config.json` |

Решения **[моё]**:
- Поток обновлений сессии main → окно идёт через длинный опрос сервиса (`waitUpdates(sessionId, afterSeq)`), потому что RPC ядра — запрос/ответ.
- Разрешения: хук `acp.toolCall` в main; если никто не решил, запрос попадает в поток обновлений сессии, окно показывает карточку, ответ уходит вызовом `respondPermission`.
- Плагины лежат в `plugins/*` отдельными пакетами; `packages/*` не импортируют `plugins/*` (линтер).
- Не входит: история после перезапуска, несколько сессий, markdown, сайдбар, островки, настройки, установка плагинов на лету.

## 11. Первый срез **[моё, пользователь не подтверждал]**

Срез проверяет весь фундамент на одном сценарии:
1. ядро с `reconcile()` и горячей перезагрузкой;
2. минимальная сборка: `storage`, `acp`, `claude-code` (сначала на неизменённом адаптере), `app`, `layout-bare`, `chat`, `composer`;
3. `layout` и `islands` как замена `layout-bare` — проверка замены раскладки;
4. `settings` и секция от другого плагина — проверка «плагин в плагине»;
5. `agent-tools` и пример стороннего плагина, который использует все четыре механизма: даёт агенту инструмент, добавляет вкладку в островки, подключается к хуку и предоставляет сервис. Пример живёт в шаблоне `create-loom-plugin`.

Глубокие хуки адаптера, остальные системные плагины и любые предметные плагины — после среза.

## 11a. Уточнения после ревью **[моё]**

**Где работают хуки.** Цепочка хука живёт в процессе, которому принадлежит действие (`acp.toolCall` — в main). Плагин окна может подключиться к хуку main через RPC, но только к асинхронным хукам и с таймаутом: если пост не ответил вовремя, вызывается `next(ctx)`. Отмена хода отменяет и ожидающие посты.

**Разрешения в минимальной сборке.** Плагин `chat` сам подключается к `acp.toolCall` последним постом и, если никто выше не решил, показывает запрос разрешения карточкой в ленте (как в Claude Code). Если окна нет или ответа нет, исход — `deny`.

**Окна и сессии.** Одно ядро в main и по одному ядру в каждом окне. Дерево расширений, `NavigationRef` и раскладка островков принадлежат окну; сервисы main общие. RPC адресует окно по его id, `reconcile()` рассылается во все окна. В первом срезе одно окно, но архитектура сразу многооконная. Несколько сессий и агентов работают параллельно; переключение — через `sessions`.

**Проект.** Проект — рабочая папка, в которой запускаются сессии агентов. Конфиг собирается слоями: сборка → пользователь (`~/.loom/`) → проект (`.loom/` в папке). Плагины проекта и его конфиг грузятся только после доверия; доверие хранится по пути папки и хэшу `.loom/`, при изменении хэша спрашиваем снова.

**Сообщения агенту от плагинов.** Плагин может отправить агенту сообщение от имени пользователя (`SessionsRef.prompt`): если агент свободен, начинается новый ход, если занят — сообщение ставится в очередь. Плагин может приложить контекст к следующему сообщению пользователя через хук `acp.prompt`.

**Установка плагинов.** Плагин поставляется собранным: по одному ESM-бандлу на вход, сторонние зависимости внутри. Общими приложение даёт только `react`, `react-dom`, `@loom/sdk`, `@loom/ui` — их версии задаёт сборка. Менеджер пакетов внутри приложения не запускается, кроме скачивания самого пакета. В `dependsOn` указываются диапазоны semver; несовместимость — установка отклоняется с объяснением.

**Сохранение состояния при перезагрузке.** Гарантируется только сохранение по стабильному id расширения и `ctx.state`: перезапуск другого или зависимого плагина не сбрасывает компонент. Замена кода самого компонента с сохранением состояния (react-refresh) — желательна в режиме разработки, но в первый срез не входит.

**Конфликт при установке на лету.** Конфликт расширений (вторая замена одного расширения без победителя) отклоняется на шаге планирования: `reconcile()` ничего не меняет и предлагает выбрать победителя; после выбора запускается снова. Конфликт сервисов (второй поставщик) обнаруживается только во время `setup` — манифест не декларирует `provides`. Затронутые плагины перезапускаются, затем происходит откат; ошибка `SETUP_FAILED` несёт id обоих плагинов (`pluginIds`) и `details.causeCode` (`SERVICE_CONFLICT`).

## 12. Что оставлено строителю

- Формат RPC между процессами (своя тонкая реализация на MessagePort/IPC с zod или готовая библиотека). Требование: сервис main доступен в окне по тому же токену, ошибки и отмена передаются.
- Как именно грузить ESM-модули плагинов в окне и делить с ними один React (import map или externals).
- Формат `loom.config.json`, кроме оговорённых ключей `disabled`, `attach`, выбора победителей в конфликтах и настроек плагинов.
- Отмена вызовов через RPC для прокси сервисов и удалённых постов хуков (этап 2): на этапе 1 она не передаётся, ожидание ограничено закрытием транспорта и таймаутом хука.
- Внутреннее устройство островков, если соблюдён контракт `islands/panels`.
- Где и как хранить сессии и историю, если `acp` умеет восстанавливать сессии после перезапуска.
