# Ядро Loom: чистка, читаемость, правила кода — проектный документ

Дата: 2026-11-05. Статус: на согласовании. Это первый из трёх проектов (1 — ядро, 2 — документация и README, 3 — контракт плагина: манифест, валидатор, линтер, скиллы, шаблон).

Условные обозначения: **[решено]** — решение пользователя; **[моё]** — решение автора документа, пользователь видел направление, но отдельно не подтверждал; **[строителю]** — на усмотрение того, кто строит.

---

## 1. Зачем

Ядро (`@loom/kernel`) должно читаться как учебник: новичок открывает исходники и по порядку понимает, как устроены плагины, сервисы, расширения, хуки, события, reconcile и RPC. Код плагинов пишется по тем же правилам, и правила проверяют инструменты, а не только ревью. **[решено]**

Заодно закрываются все известные проблемы ядра: отложенные замечания ревью первой стадии и ограничения из `docs/kernel/README.md` («пофиксить все вопросы и проблемы»). **[решено]**

Плагинам доверяем полностью — механизмы доверия удаляются целиком. **[решено]**

## 2. Цели, не-цели, анти-цели

**Цели**
- Удалить всё, что связано с доверием (§4).
- Закрыть все отложенные проблемы ядра (§5) — каждая либо исправлена с тестом, либо (если это осознанный контракт) превращена в явную гарантию в коде и доках.
- Проход читаемости по всему `packages/kernel`, `packages/sdk` (§6).
- Правила кода и линтеры для всего репозитория, включая плагины (§7).
- Слить `@loom/host` в `@loom/sdk` (§8).
- Сузить публичный API `@loom/kernel` до того, что нужно хосту (§8).

**Не-цели**
- Документация для авторов плагинов, `ARCHITECTURE.md`, README — проект 2. Здесь только комментарии в коде, обзоры файлов и порядок чтения ядра.
- Манифест, валидатор, `eslint-plugin-loom`, скиллы, шаблон, проверка версий — проект 3.
- Новые возможности ядра. Поведение для плагинов меняется только там, где это перечислено в §4 и §5 (удаление доверия и исправление дефектов); до 1.0 такие изменения допустимы без слоя совместимости. **[моё]**
- Плагины `acp`, `chat` и др.: их код приводится к новым правилам линтера (§7), но их отложенные замечания — вне этого проекта.

**Анти-цели**
- Комментарии-пересказы сигнатур («`id` — идентификатор»). Комментарий, не добавляющий смысла, хуже его отсутствия.
- Дробление глубоких модулей на десятки функций по 5 строк ради метрик.
- Падение производительности: перф-тесты (`pnpm test:perf`) и бенчмарки ядра не хуже текущих.
- Покрытие ниже 95% по пакету.

## 4. Удаление доверия **[решено]**

Удаляется полностью, из кода, тестов, доков, спеки:
- `KernelOptions.trust` и проверка в `kernel-runtime.ts` (`trusted()`).
- Код ошибки `UNTRUSTED`.
- Поле `PluginDefinition.scope` (`builtin | user | project`) — используется только доверием; из схемы `manifest.ts` и из загрузчика `node/loader.ts` (он больше не штампует scope). **[моё]**
- `BeforeInstallHook`, код `INSTALL_DENIED`, их использование в `PluginsService.install/reload`.
- `trust: () => true` в `apps/desktop` (main и renderer).
- Связанные упоминания в `docs/kernel/README.md` и в спеке `2026-11-04-loom-design.md`.

## 5. Проблемы ядра, которые закрываются

Источник полного списка — «minor (deferred)» в `.superpowers/sdd/2026-11-04-loom-kernel/progress.md` (stage 1) и раздел «Известные ограничения» `docs/kernel/README.md`. Строитель проходит **каждый** пункт; ниже — решения по тем, где есть выбор.

**Известные ограничения**
| Ограничение | Решение |
|---|---|
| Глубина дерева ≈ 3000 (рекурсия) | Разрешение дерева итеративное; тест на глубину 10 000. **[моё]** |
| Квадратичный объём ошибок сирот в цикле `attachTo`; `reasonFor` кубический | Каждая сирота сообщает ближайшую причину, цепочка считается один раз; линейно. **[моё]** |
| Подписка на один тип события O(n²) | Снимок списка делается лениво только при `emit` во время изменения (версия списка), подписка O(1). **[моё]** |
| `run` в `setup` упорядочивает хук немедленно, O(n² log n) | Упорядочивание ленивое и инкрементальное: пересчёт только при изменении тапов этого хука. Если инкрементальность выходит за 1 день работы — оставить, задокументировав сложность в комментарии модуля. **[строителю]** |
| Определения неизменяемы — контракт | `definePlugin` замораживает **структуру определения**: сам объект, `dependsOn`/`optionalDependsOn`, массив `extensions` и объекты-определения расширений, массивы `before`/`after`. Значения, которые плагин передаёт внутрь (конфиг, компоненты, схемы, `defaults`), не замораживаются — это данные плагина. Мутация структуры бросает в strict mode. **[моё]** |
| `disable` = удаление, состояние теряется | Остаётся (осознанный контракт), закрепляется в JSDoc `PluginsService.disable` и в тесте. |
| `dispose()` идемпотентен, но после провала возвращает тот же отклонённый промис | Остаётся; JSDoc говорит это явно. |
| Кэш semver сбрасывается целиком | LRU не нужен; остаётся, комментарий в коде. **[моё]** |

**Отложенные замечания (группы)**
- Корректность: прокси сервиса без провайдера бросает на `then`/`toStringTag` (await/лог прокси); `onChange` на регистрациях без смены активной реализации; поверхностный снимок `ctx.state` при откате; откат поднимает версии сервисов → лишняя пересборка дерева; `reload()` после `dispose` бросает синхронно вместо rejection; `enable(unknown)` с неверным кодом; повторное сообщение о противоречивых ограничениях хуков; дубликат `tapId` от пира; голый endpoint без приёмника молча теряет битые сообщения; поздний tap-result после таймаута; схема плагина не строгая (`dependOn` проходит), `validRange("")`, `"v1.0.0"`.
- Ресурсы: индексы `states`/`registered` не сжимаются; `prompted`-подобные наборы.
- Тесты: отсутствующие ветки (реентерабельный `emit`, не-Error из слушателя, падающий `onError`, приоритеты ошибок графа), свойства-тесты с пробелами, неверно сгруппированные `describe`, ярлыки R13/R14 в названиях тестов, `test:coverage` перечисляет проекты (новый проект ускользает от покрытия).
- Инфраструктура: depcruise видит только tsconfig ядра; запрет `@loom/sdk` только в блоке core; нет фикстур, доказывающих срабатывание правил границ; api-extractor на TS 6 против TS 5.9 репозитория.
- Мелочи стиля: лишние касты, функция `describe` в коде, пустые строки.

Пункты, связанные с удалённым доверием (кэш `trust`), снимаются вместе с §4.

**Объём и критерии** **[моё]**
- В объёме: все «minor (deferred)», «triage at final review» и пункт «Final: minor» журнала stage 1, а также итоговые находки финального ревью stage 1. Пункт, уже исправленный на `feat/minimal-build` (например, R21 — RPC классовых сервисов), отмечается «уже исправлено (коммит)».
- Вне объёма: отложенные замечания stage 2 (плагины `acp`, `chat`, `apps/desktop`).
- «Снято» допускается только в двух случаях: код удалён (§4, §8), или исправление стоит заметно дороже проблемы — тогда причина и оценка пишутся в отчёт, а поведение закрепляется в JSDoc. Всё остальное исправляется с тестом.

**Решения по исправлениям, меняющим поведение** **[моё]**
| Дефект | Новое поведение |
|---|---|
| Нестрогая схема плагина | Схема строгая: неизвестный ключ, `"v1.0.0"`, пустой диапазон → `MANIFEST_INVALID` с путём поля в `details` |
| Прокси без провайдера бросает на `then` / `Symbol.toStringTag` | `then` → `undefined` (прокси можно `await`/логировать), `toStringTag` → `"LoomService(<id>)"`; любой другой член по-прежнему `SERVICE_MISSING` |
| `onChange` без смены активной реализации | Срабатывает только при смене активной реализации |
| `enable(unknown)` → `DEPENDENCY_MISSING` | Новый код `PLUGIN_UNKNOWN`; `disable/uninstall(unknown)` — тоже `PLUGIN_UNKNOWN` без прохода reconcile и без `plugins.changed` |
| `reload()` после `dispose` бросает синхронно | Возвращает отклонённый промис с `DISPOSED`, как остальные методы |

## 6. Читаемость ядра

**Порядок чтения** **[моё]**
- Файлы `src/core` раскладываются так, чтобы читать сверху вниз: понятия → определения → реестры (сервисы, хуки, события, дерево) → план и граф → reconcile → runtime → фасад `createKernel`. Конкретный способ (нумерация папок, `README` в `src/` со списком файлов по порядку, или переименование) — **[строителю]**, но порядок обязан быть виден в репозитории без IDE.
- В начале каждого файла ядра — обзорный комментарий 3–8 строк: роль файла, на что опирается, кто его использует, чего он никогда не делает (инвариант).

**Комментарии в коде** **[решено: «JSDoc, небольшой, но описывающий основной функционал»]**
- Каждый экспорт (функция, класс, интерфейс, тип, константа, ref сервиса/хука): 1–2 фразы — что обещает, гарантии, ошибки (`LoomError`-коды), побочные эффекты. Без пересказа типов, без `@param` с повтором имени.
- Внутренние функции — комментарий только там, где «почему» неочевидно (инвариант, порядок, почему короткий путь безопасен).
- Тесты читаются как спецификация: имя теста — поведение («откат возвращает сервисы предыдущего прохода»), без ярлыков ревью.

**Правила кода** **[моё, по итогам исследования Google TS Style Guide, Effective TypeScript, Total TypeScript, Ousterhout]**
- Имена: целые слова; без `I`/`_`-префиксов; булевы `is/has/can/should`; единицы в имени (`timeoutMs`).
- Форма объекта — `interface`, объединения и производные — `type`.
- Именованные функции — `function`-объявления; стрелки — для колбэков.
- Больше трёх позиционных параметров или булев флаг → объект опций (`max-params: 3`).
- Публичные сигнатуры без «гимнастики типов»; сложные типы — внутри модулей.
- Недопустимые состояния непредставимы: размеченные объединения вместо пачки опциональных полей.
- Один файл — одно понятие; реэкспорт только в корневом `index.ts` пакета.
- Модули глубокие: узкий интерфейс; не дробить ради метрик.
- Ошибки — только `LoomError` со стабильным кодом; пустой `catch` — только с комментарием-причиной.

Правила записываются в корневой `AGENTS.md` (раздел «Код») и `packages/kernel/AGENTS.md` (порядок чтения, инварианты ядра). `CLAUDE.md` в корне — одна строка `@AGENTS.md`. **[решено: «правила клода, AGENTS.md»]** Остальные `AGENTS.md`, скиллы и шаблон плагина — проект 3.

## 7. Линтеры **[решено: «везде, где возможно, линтеры»; набор — моё]**

Добавляются ко всему репозиторию (`packages/*`, `plugins/*`, `apps/*`), существующий код приводится к ним:
- `sonarjs/cognitive-complexity`: 15.
- `max-depth`: 4; `max-params`: 3.
- Код укладывается в лимиты переработкой, а не дроблением ради метрики. Если глубокий модуль честно сложнее лимита, допускается точечный `eslint-disable-next-line <правило> -- <причина>`; каждый такой случай перечисляется в отчёте, их не больше пяти на репозиторий. **[моё]**
- `@typescript-eslint/switch-exhaustiveness-check`.
- `@typescript-eslint/naming-convention`: только булевы (`is/has/can/should/was/did`) и запрет `I`-префикса интерфейсов.
- `simple-import-sort` (импорты и экспорты), с автофиксом.
- Документация публичного API: api-extractor `ae-undocumented: error` для `@loom/kernel` и `@loom/sdk` (у ядра появляется свой отчёт API).
- Документация непубличного: `jsdoc/require-jsdoc` (`publicOnly: true`) + `jsdoc/require-description` + `jsdoc/no-types` + `tsdoc/syntax` для `src` всех пакетов и плагинов (включая `packages/react` и `apps/desktop`). Значит, в этом проекте экспорты плагинов тоже получают 1–2-фразовые комментарии по правилам §6. **[решено: «везде, где возможно»]**
- Не включаются: `unicorn/prevent-abbreviations`, пресет perfectionist, `eslint-plugin-functional`, `consistent-type-definitions`, `max-statements`.

Каждый плагин ESLint проверяется на совместимость с ESLint 10 (peer-диапазон, `context.sourceCode`); несовместимый — через `@eslint/compat` `fixupPluginRules` или заменяется. Если совместимой версии нет и обёртка не помогает — правило выпадает с записью причины в отчёте. **[строителю]**

Для новых правил — фикстуры в `tools/check-lint-fixtures.mjs`, доказывающие срабатывание (как для правил границ).

## 8. Пакеты и публичный API

- `@loom/host` вливается в `@loom/sdk`: `HostRef` и `Host` экспортируются из SDK; пакет удаляется; все импорты в плагинах и `apps/desktop` переводятся. **[моё, пользователь видел предложение]**
- `@loom/kernel` остаётся источником всего авторского API (`definePlugin`, `createServiceRef`, `createHook`, `createExtension`, `attach`, `PluginsRef`, `DisposableStore`, `LoomError`, типы) и всего RPC (`createRpcEndpoint`, `createMemoryTransportPair`, `exposeServices`, `exposeHooks`, `provideRemoteServices`, `remoteServicesPlugin`, `tapRemote`), плюс `createKernel` и загрузчик (`/node`); SDK реэкспортирует авторскую часть как сейчас, без `BeforeInstallHook`. Внутренние фабрики (`createServiceRegistry`, `createHookRegistry`, `createEventBus`, `buildTree`, `createPluginContext`, `resolveOrder`, `dependentsOf`, `validatePlugin`) перестают быть публичными, если ими никто вне пакета не пользуется; тесты импортируют их из `src`. **[моё]** Строитель проверяет использование по репозиторию перед удалением экспорта.

## 9. Как понять, что готово

- `pnpm check`, `pnpm test:coverage` (≥95% по ядру и SDK), `pnpm test:perf`, `pnpm --filter @loom/desktop e2e` зелёные; CI зелёный.
- В коде, тестах и доках нет `KernelOptions.trust`, `UNTRUSTED`, `PluginDefinition.scope` (и его штамповки в загрузчике), `BeforeInstallHook`, `INSTALL_DENIED`. Посторонние значения слова — например `storage.scope(ns)` — не затрагиваются.
- Каждый пункт «minor (deferred)» stage 1 и каждое известное ограничение имеет в отчёте строку: исправлено (тест) / закреплено как контракт (где) / снято (почему).
- Каждый файл `packages/kernel/src` начинается с обзорного комментария; порядок чтения виден в репозитории.
- api-extractor не выдаёт `ae-undocumented`; ESLint чист с новыми правилами.
- Раздел «Известные ограничения» в `docs/kernel/README.md` обновлён под фактическое состояние (полное переписывание доков — проект 2).
